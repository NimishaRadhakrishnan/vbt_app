Findings

Seven of these returned a 500 to a real user. None of them failed a test — which is the reason they survived this long, and why the last two were only found by driving the actual screens.

Show
01
Fixed

Deleting a farmer or dealer returned 500

visits.farmer_id was ON DELETE SET NULL while check_visit_target required it to be non-null. The two constraints contradicted each other, so deleting any farmer who had ever been visited raised a check violation and the request died. The delete could never have succeeded.

The endpoint also checked nothing, logged nothing, and returned {"status":"success"} for a farmer that did not exist.

Foreign keys are now RESTRICT, matching the policy already used for the other history tables. The endpoint archives a farmer who has visits, deletes one who has none, 404s on a missing id, and writes an audit entry either way.

Evidence: migration 202609290001 · test_farmer_delete.py, 3 tests
02
Fixed

Roster status returned 500 on every call

A fix for the UTC day-boundary bug added from app.domain.services.time_utils import … inside the function body. That module does not exist. timedelta was never imported either.

Because the import was nested in the function, it only failed when a request arrived — so it passed every import check and the entire test suite. In the browser it surfaced as a CORS error, because the 500 carried no CORS headers, which hid the real cause completely.

A source guard now resolves every import target in every router and fails on one that points at nothing. It was confirmed by reintroducing the exact bug, then removing it again.

Evidence: test_dashboard_endpoints_smoke.py · guard proven to fail and pass
03
Fixed

Refreshing any page logged the admin out

GET /auth/me answered a missing token with 403 — FastAPI's HTTPBearer default. The web client only attempts a silent token refresh on 401, so after any reload the refresh never fired and the user was returned to the login screen. Bookmarks and deep links never worked.

get_current_user now raises 401 itself; 403 stays reserved for "authenticated but not permitted".

Evidence: confirmed in a real browser · test_auth_flow.py
04
Fixed

An invalid visit purpose returned 500

The API schema did not constrain the field, so an unexpected value reached Postgres and tripped ck_visit_trial_purpose. Officers saw a bare 500. The schema now mirrors the constraint and returns a 422 naming the allowed values. trial_plot_size_cents was ge=0 against a database constraint of > 0; also corrected.

An existing test had been passing on a coincidence — its payload carried an invalid purpose, and the stock check happened to answer 400 before the row reached the database. Its payload is now valid, so it tests what its name says.

Evidence: test_stock_walkthrough.py
05
Fixed

The login screen rejected correct passwords

"Select Your Role" defaulted to Field Officer. An admin entering the right credentials was logged in, the app compared the account's real role to the dropdown, logged them straight back out, and showed "This account is registered as a Admin."

The dropdown gated nothing — roles are enforced server-side — and could only ever cost a login. Removed.

Evidence: login verified in a browser after the change
06
Fixed

Seven tables belonged to a different product

The repository was scaffolded from an MCP Server Risk Scanner project and its migrations came along: mcp_servers, tool_capabilities, risk_findings, risk_cards, governance_recommendations, alerts, connections, policies. No file under app/ referenced any of them. The two Marketing tables were also still present after that module was cut.

The app identified itself as APP_NAME="MCP Server Risk Scanner", and the browser stored its session under mcp_scanner_refresh_token. Both renamed.

Evidence: migration 202609290002 — ten tables dropped in dependency order
07
Fixed

The demo seed could only ever run once

It cleared tables from a hand-written list, so the first table it missed (kudos) made DELETE FROM users fail on a foreign key and rolled the whole seed back. It now asks pg_constraint which tables actually block a delete and clears those, leaving the day-closure form configuration that migrations own intact.

Evidence: run three times in a row, config row counts unchanged
08
Fixed

Smaller corrections

An over-broad fixture ran DELETE FROM farmers WHERE name = 'Test Farmer' across all modules, taking eight unrelated tests down with it. A test pointed at /api/v1/daily-visit-tracker/… when the real route is /api/v1/visits/daily-tracker/… and had been left failing. bcrypt pinned to 4.0.1, which stops a trapped stack trace on every password hash. Off-brand indigo and blue primary buttons brought to the maroon brand colour. Missing alt on visit photos. Login fields given real autocomplete values.

About 50 patch_*.py scratch files, ad-hoc debug scripts, a committed virtualenv and a committed build output removed — the tree went from 895 MB to roughly 5 MB excluding dependencies.

Evidence: .gitignore extended so none of it returns
09
Config

Brute-force protection was off in code, not just in the env file

Settings declared 5000 attempts per 1 second. That is the limiter switched off, and it applied even with no .env present — so a clean deployment inherited it.

Tightening the numbers alone would have made things worse. The counter was keyed on client IP, and officers reach the API over mobile networks that put a whole region behind a few addresses: a five-attempt IP limit would let one colleague's typo lock out the rest. It was also too weak in the other direction, since an attacker simply rotates addresses.

Throttling now counts failures, not sign-ins. The dependency in front of login reads the counters; the increment happens on the failure path. A correct password costs nothing and clears the account's counter. Five failures per five minutes per account; one hundred per source address; Redis unreachable fails open, because a limiter that cannot reach its store must not lock out the field force.

A wrong first attempt, recorded because it is the useful part: the first version counted every attempt against a 50-per-5-minutes IP bucket. It passed in isolation, then failed when the packaged build was re-verified from scratch — ordinary sign-ins exhausted the bucket and cascaded into 17 failures. In the field that is a district checking in at nine in the morning.
10
Config

The CORS allowlist did nothing

An allow_origin_regex of https?://.* sat next to the allowlist. Starlette treats the regex as an OR, and that pattern matches every origin there is — so the allowlist was decorative and, with credentials enabled, any site a signed-in admin visited could call this API with their session.

The regex is gone. Outside production a narrow localhost pattern remains so development servers on arbitrary ports still work.

Evidence: unlisted origin refused in both environments · test_security_config.py
11
Config

Secrets regenerated

The development .env has a freshly generated JWT key and the corrected login limits. The key that was committed to the repository's history is no longer in use — anyone with a copy of that history could mint a valid admin token with it.

backend/.env.production.example is filled in and ready: production environment, debug off, correct limits, a separate generated JWT key and a generated database password.

Those keys travelled through a chat and a zip. Regenerate on the server with openssl rand -hex 32 if you want one that has never left the machine. Rotating the JWT key signs out every existing session — harmless before launch.

Evidence: shipped .env confirmed to differ from the committed key
12
Config

A startup guard, so none of this regresses quietly

In production the app now refuses to start when debug is on, the JWT key is a known example or shorter than 32 characters, the login limit is above 10 attempts or the window under 60 seconds, or the CORS list holds a wildcard. It fails at boot with the specific reasons listed. Development is never blocked.

Every one of those values was live in the shipped .env at least once. None of them break anything visibly — the app starts, the login page loads, and the weakness is invisible until it is exploited. Boot is the only moment it reliably gets noticed.

Evidence: test_security_config.py — each unsafe setting refused, a correct one accepted
13
Fixed

Sixteen business rules reached the user as server crashes

raise ValueError("You have already checked in for today.") — and fifteen more like it across the application layer. No handler mapped ValueError, so every one fell through to the catch-all and the officer was shown "An unexpected error occurred. Our team has been notified."

The messages were already written for a person, and none of them ever arrived. An officer who taps check-in twice, or whose first request succeeded while the reply was lost on a rural connection, saw a crash instead of an explanation.

Two domain exceptions were added and all sixteen sites converted — 409 where the request would duplicate something, 400 otherwise. A source guard fails the build if a bare ValueError reappears in the application layer.

Found by: driving the real UI, not by reading code — the check-in call returned 500 with a perfectly good message behind it. Now: 409 {"message": "You have already checked in for today."}
14
Fixed

The Stock History screen was permanently blank

GET /stock/ledger with no officer_id fell back to the caller's own id. Admins hold no stock, so an admin asking for the whole movement history was silently asking for their own and always got an empty list — and the History tab calls it exactly that way.

The movement audit trail, which is the thing that makes an append-only ledger worth having, could not be reached from the UI at all. The docstring said "admin/manager see anyone's". The code never did.

An officer now sees their own, an admin a named officer's or — with no filter — everyone's. Widening the admin case did not widen the officer case: an officer passing someone else's id still gets only their own.

Evidence: History now lists the +50 allocation and the −5 trial with the officer's name · two tests, both confirmed to fail when the old line is restored

Still open

None of this blocks a submission. None of it should be described as done.

Design decisions not made for you

  • Sub-pages lose the navigation. Overview has the maroon header and the sidebar; Field Network has neither; Products has a dark navy header. Three page chromes — the most visible inconsistency in the product.
  • At 1440px the Overview content column stops around 770px, leaving a wide empty band. Other pages run full width.
  • On Field Network, Delete is the only action on a farmer card, and its red tint makes it the most prominent thing on the row. There is no view or edit.

Not done

  • dashboard/page.tsx is 5,096 lines. It builds and works, but every change to it carries more risk than it needs to.
  • No automated tests for the frontend or the mobile app. All 187 are backend.
  • The mobile app was not built or run — no Android toolchain was available. Its code was not changed.
  • Admin password viewing was never implemented. Existing passwords are bcrypt-hashed and unrecoverable by anyone, including you.

Deployment

Do first

CORS_ALLOWED_ORIGINS still reads http://localhost:3000. It is the one value in the production template that is certainly wrong, and the API will refuse the real portal until it is changed.

  1. Copy the template. cp backend/.env.production.example backend/.env
  2. Set the portal origin. The real domain, not localhost.
  3. Match the database password on the Postgres service.
  4. Optionally regenerate the JWT key and database password with openssl rand -hex 32, so neither has ever left the server.
  5. Set a Redis password and keep Redis off the public network — it holds live officer positions and refresh-token state.
  6. Build and start. If the backend refuses to boot, read the error: the guard lists exactly which settings it objected to. That is the guard working, not a failed deploy.
  7. Migrate. docker compose exec backend alembic upgrade head
  8. Create the real admin account and change every seeded password. The demo accounts and their shared password are published in the demo script below.
# the whole thing, from a clean machine
docker compose up -d postgres redis
docker compose up -d --build backend frontend scheduler
docker compose exec backend alembic upgrade head
docker compose exec backend python -m pytest tests/ -q

What the CEO sees

2 min

Sign in as the administrator. Point at three things and move on: Active Officers, how many of the field force are checked in right now; Needs attention, unresolved crop-disease questions and plans awaiting approval; and Live officer tracking, which opens the map.

Needs attention is a work queue, not an alert list. It persists until someone acts, which is the point — it does not reset overnight.

This screen is built from what officers actually did today, not from what anyone typed into a report.

Stock, the part that has to be right

4 min

The strongest sequence in the demo, because one number moves through three screens and stays consistent.

  1. Admin Stock → Issue Stock. Choose Dinesh Prabhu, enter 50 against Bio-NPK Liquid, submit.
  2. Sign in as Dinesh in a second browser profile or on the phone. My Stock reads 50.
  3. Log a visit from the Daily Visit Tracker. Mark it a trial, give 5 units.
  4. Re-open My Stock. It reads 45.
  5. Back as admin, Admin Stock → History shows both movements, each with who did it and when.

Then show the guard: as Dinesh, try to give 999 units. The submission is refused and the balance is still 45 — nothing was written.

An officer's stock is not a number we store and hope stays right. It is the sum of every movement ever recorded, so it cannot drift out of step with the history.

The field officer's day

3 min

Sign in as Karthik. Check in — the app asks for location permission with a plain-language disclosure first, and explains that tracking stops at check-out. Walk through a farmer visit in the Daily Visit Tracker: farmer details, crop, what was observed, any trial given, photos. Then Day Closure: distance travelled, expenses, what was completed.

Back as admin, open Daily Visit Reports to show the same visit from the other side, and Movement History to replay the officer's route.

Admin control

3 min
  1. User Management — create an officer, edit, disable, delete. A user with history is archived rather than destroyed, and the app says so. The last remaining admin cannot be deleted.
  2. Products — add a product, then issue stock against it immediately.
  3. Day Closure Form Builder — add a field and show it appearing on the officer's side.
  4. Knowledge Base — an expert's answer to a crop-disease question is published automatically, so the same question from another officer is already answered.
Every figure on the admin screens traces back to a specific action by a specific officer at a specific time. There is no separate reporting step to fall behind.
